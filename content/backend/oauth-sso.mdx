## 1. Introduction

**What is this lesson?**
In this lesson, we will learn about **OAuth 2.0 (Open Authorization)** and **SSO (Single Sign-On)**. These are the protocols that power buttons like "Login with Google", "Login with GitHub", and "Continue with Apple".

**Why are we learning it?**
Users hate creating new passwords. If you force a user to create a new account from scratch, 50% of them will simply leave your website. Adding social login drastically increases user sign-ups and removes the liability of storing passwords in your own database.

**Why should a backend engineer know this?**
Implementing an OAuth flow is notoriously tricky. It involves redirecting the user to another website, waiting for a callback, exchanging temporary codes for access tokens, and fetching user data. If you get it wrong, a hacker can hijack the OAuth flow and log into someone else's account.

---

## 2. Why This Exists

**What problem existed before?**
Imagine you build an app that prints out people's Yelp reviews. In the year 2005, your app would literally ask the user: *"Please type your Yelp Username and Yelp Password into my app."* Your app would then log into Yelp pretending to be the user to read their reviews. This was called the "Password Anti-Pattern." It was incredibly dangerous because users were giving away their raw passwords to random third-party apps!

**Why was this technology created?**
In 2006, Twitter and Google realized they needed a way for a user to grant a 3rd-party app access to their data *without* giving the 3rd-party app their password. This led to the creation of OAuth.

**How did companies solve this problem?**
OAuth introduced **Delegated Authorization**. Instead of asking for a password, the 3rd-party app redirects the user to Google. Google asks the user, *"Do you want to let this app read your email?"* If the user clicks Yes, Google gives the 3rd-party app a temporary, revocable "Access Token" (like a hotel keycard) that can *only* read emails and nothing else.

---

## 3. Problems It Solves

**Without OAuth, you have a massive security liability.**
If you store 1 million user passwords in your database and you get hacked, you are on the front page of the news. 

**With OAuth, Google takes the risk.**
You never touch the user's password. Google authenticates the user, secures their password, forces them to use Two-Factor Authentication (2FA), and simply hands you a Token saying, "Yes, this is definitely Rahul."

## 4. Real Life Analogy

<AnalogyCard title="The Valet Key">
  Think of OAuth like a **Valet Key** for your car.

  Normally, your car key (Password) can open the doors, start the engine, open the glovebox, and open the trunk. 

  When you go to a fancy restaurant, you give the Valet Driver a special Valet Key (OAuth Access Token). This special key can *only* start the engine and open the driver's door. It is physically impossible for the Valet Key to unlock the glovebox where your valuables are stored. 

  OAuth allows you to give an app a "Valet Key" to your Google Account that can only read your Email Address, but cannot read your Google Drive files or change your password!
</AnalogyCard>

## 6. Step-by-Step Explanation

Let's break down the most secure OAuth flow: the **Authorization Code Grant**.

**Step 1: The Request (Clicking the Button)**
↓
The user clicks "Login with Google" on your website. Your frontend redirects their browser to Google's special OAuth URL, including your `client_id` (so Google knows which app is asking).

**Step 2: The Consent Screen**
↓
The user logs into Google (if not already) and sees a screen: *"QuizKaal wants to access your name and email. Allow?"* The user clicks "Allow".

**Step 3: The Redirect Callback**
↓
Google redirects the user's browser back to your website (e.g., `quizkaal.com/callback?code=xyz123`). Notice the `code` in the URL! This is the **Authorization Code**.

**Step 4: The Backend Exchange (Secret)**
↓
Your frontend sends the `code` to your Node.js Backend. Your Backend sends an HTTP `POST` request directly to Google containing the `code` AND your `client_secret`. 

**Step 5: The Access Token**
↓
Google verifies the `code` and the `secret`, and replies to your Backend with an **Access Token** (and sometimes an ID Token or Refresh Token).

**Step 6: Fetching User Data**
↓
Your Backend uses the Access Token to make an API call to Google: `GET /userinfo`. Google replies with: `{"name": "Anisul", "email": "anisul@example.com"}`. Your Backend saves this in the database and logs the user in!

## 7. Deep Explanation: Scopes and SSO

<ConceptBlock type="info" title="Scopes & Single Sign-On">
  **Scopes**
  When you redirect the user to Google, you must specify what you want. This is called a `Scope`. 
  - `scope=profile email` (You just want to log them in).
  - `scope=https://www.googleapis.com/auth/calendar` (You want to read/write to their Google Calendar).
  The user will see exactly what Scopes you requested on the Consent Screen.

  **SSO (Single Sign-On)**
  SSO is an enterprise implementation of OAuth/SAML. In a large company, an employee shouldn't have to create a password for Slack, Jira, Zoom, and GitHub. With SSO, the company uses a central Identity Provider (like Okta or Microsoft Entra). The employee logs into Okta once, and Okta uses OAuth/SAML to instantly log them into all 50 company apps!
</ConceptBlock>

## 8. Node.js Implementation

Implementing OAuth from scratch is hard because of the cryptographic verifications required. In the Node.js ecosystem, backend engineers almost always use **Passport.js**, which handles all the redirects, code exchanges, and token validation for you!

<CodeTabs>
  <div label="oauth-server.js (Node.js)">
    ```javascript
    const express = require('express');
    const passport = require('passport');
    const GoogleStrategy = require('passport-google-oauth20').Strategy;

    const app = express();

    // 1. Configure Passport with your Google Developer Credentials
    passport.use(new GoogleStrategy({
        clientID: 'YOUR_GOOGLE_CLIENT_ID',
        clientSecret: 'YOUR_GOOGLE_CLIENT_SECRET',
        callbackURL: "http://localhost:3000/auth/google/callback"
      },
      function(accessToken, refreshToken, profile, done) {
        // Step 6! Google sent us the user's profile.
        console.log("User's Google Profile:", profile.displayName, profile.emails[0].value);
        
        // Here, you would find or create the user in your Database!
        // const user = await User.findOrCreate({ googleId: profile.id });
        
        return done(null, profile);
      }
    ));

    // 2. The Login Route (Step 1)
    // When the user clicks "Login", we redirect them to Google asking for 'profile' and 'email' scope.
    app.get('/auth/google',
      passport.authenticate('google', { scope: ['profile', 'email'] })
    );

    // 3. The Callback Route (Step 3 & 4)
    // Google redirects the user back here with the `code`. Passport automatically exchanges it!
    app.get('/auth/google/callback', 
      passport.authenticate('google', { failureRedirect: '/login' }),
      function(req, res) {
        // Successful authentication!
        console.log("OAuth Flow Complete! Sending user to dashboard.");
        res.redirect('/dashboard');
      }
    );

    app.listen(3000, () => console.log('OAuth Server running on Port 3000'));
    ```
  </div>
</CodeTabs>

**Expected Flow:**
1. You open `http://localhost:3000/auth/google`.
2. The browser is violently redirected to `accounts.google.com`.
3. You select your Google Account.
4. The browser is redirected back to `/auth/google/callback`.
5. The Node.js terminal logs your Name and Email!

## 10. Common Mistakes

<WarningCard title="Leaking the Client Secret">
  **The Mistake:** Putting the `client_secret` directly into your frontend React code.

  **Why it happens:** Beginners think "My React app needs to exchange the code for the token, so I will put the secret in my React `.env` file."

  **The Fix:** NEVER put the Client Secret in the frontend. If a hacker finds it, they can spoof your app and steal user data. The OAuth exchange (Step 4) MUST happen on your secure Node.js backend where the secret is safely hidden in your backend `.env` file!
</WarningCard>

## 11. Best Practices

**State Parameter to Prevent CSRF:**
When redirecting the user to Google, always include a random string called `state` in the URL. When Google redirects back, it will include that exact same `state`. Your backend verifies it matches. This prevents Cross-Site Request Forgery (CSRF) attacks where a hacker tries to log a victim into the hacker's own account!

**OIDC (OpenID Connect):**
OAuth 2.0 was designed for *Authorization* (giving access to APIs). It wasn't actually designed for *Authentication* (proving who the user is). To fix this, the industry built **OpenID Connect (OIDC)** on top of OAuth. OIDC introduces the **ID Token** (a JWT) alongside the Access Token, which explicitly contains the user's identity data.

---

## 12. Performance & Security

**Security (The Implicit Flow is Dead):**
In the old days, Single Page Apps (like React) couldn't use the secure "Authorization Code" flow because they couldn't keep a secret. They used the "Implicit Flow", where Google returned the Access Token directly in the URL! This was incredibly dangerous (tokens logged in browser history).
Today, we use **PKCE (Proof Key for Code Exchange)**. PKCE allows frontend apps to securely use the Authorization Code flow without needing a hardcoded Client Secret by generating cryptographic challenges on the fly.

## 15. Summary

*   **OAuth 2.0** allows users to grant 3rd-party apps access to their data without sharing passwords.
*   The **Authorization Code Flow** is the most secure method, separating the frontend redirect from the backend secret exchange.
*   **Scopes** define exactly what permission the app is requesting.
*   **SSO** allows enterprise users to log in once (via Okta) and access dozens of internal applications instantly.
