## What is RAG?

**Retrieval-Augmented Generation (RAG)** is a technique that gives LLMs access to **external knowledge** by retrieving relevant documents before generating an answer.

<AnalogyCard
  title="The Open-Book Exam"
  description="Without RAG, an LLM is taking a closed-book exam — it can only answer from what it memorized during training. With RAG, the LLM gets to bring a textbook (your documents) to the exam. It can look up the relevant pages before writing its answer. This means it can answer questions about YOUR data — company policies, product docs, research papers — that it was never trained on."
/>

### Why RAG Exists

LLMs have two fundamental limitations:

1. **Knowledge cutoff:** GPT-4 doesn't know what happened after its training data ended
2. **No private data:** It has never seen your company's internal documents

RAG solves both by **retrieving** relevant context at query time and **injecting** it into the prompt.

## The Naive RAG Pipeline

```
┌─────────┐    ┌────────┐    ┌────────┐    ┌──────────┐    ┌──────────┐
│  Load   │ →  │ Chunk  │ →  │ Embed  │ →  │  Store   │ →  │  Index   │
│Documents│    │  Text  │    │Vectors │    │in VecDB  │    │ Complete │
└─────────┘    └────────┘    └────────┘    └──────────┘    └──────────┘

At query time:
┌────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  User  │ →  │  Embed   │ →  │ Retrieve │ →  │ Generate │
│ Query  │    │  Query   │    │ Top-K    │    │ Answer   │
└────────┘    └──────────┘    └──────────┘    └──────────┘
```

### Step-by-Step Implementation

```javascript
import { ChatOpenAI, OpenAIEmbeddings } from "@langchain/openai";
import { RecursiveCharacterTextSplitter } from "langchain/text_splitter";
import { MemoryVectorStore } from "langchain/vectorstores/memory";
import { createRetrievalChain } from "langchain/chains/retrieval";
import { createStuffDocumentsChain } from "langchain/chains/combine_documents";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { PDFLoader } from "langchain/document_loaders/fs/pdf";

// === INDEXING PHASE ===

// 1. Load documents
const loader = new PDFLoader("./company-handbook.pdf");
const docs = await loader.load();

// 2. Chunk the documents
const splitter = new RecursiveCharacterTextSplitter({
  chunkSize: 1000,
  chunkOverlap: 200,
});
const chunks = await splitter.splitDocuments(docs);

// 3. Embed and store
const vectorStore = await MemoryVectorStore.fromDocuments(
  chunks,
  new OpenAIEmbeddings()
);

// === RETRIEVAL PHASE ===

// 4. Create retriever
const retriever = vectorStore.asRetriever({ k: 4 });

// 5. Create the generation chain
const prompt = ChatPromptTemplate.fromTemplate(`
  Answer the question based ONLY on the following context:
  
  {context}
  
  Question: {input}
  
  If the context doesn't contain the answer, say "I don't have 
  enough information to answer this question."
`);

const model = new ChatOpenAI({ model: "gpt-4" });
const combineDocsChain = await createStuffDocumentsChain({ llm: model, prompt });
const chain = await createRetrievalChain({ combineDocsChain, retriever });

// 6. Ask a question
const response = await chain.invoke({
  input: "What is our company's vacation policy?"
});

console.log(response.answer);
// "According to the handbook, employees receive 20 days of PTO per year..."
```

## Chunking Strategies

The way you split documents **directly impacts retrieval quality**. There is no universal best size — it depends on your content and queries.

### Common Strategies

| Strategy | How It Works | Best For |
|----------|-------------|----------|
| **Fixed Size** | Split every N characters | Simple, predictable |
| **Recursive** | Split by paragraph → sentence → word | Most documents |
| **Semantic** | Split when the topic changes | Research papers |
| **Markdown/HTML** | Split by headers and sections | Documentation |

```javascript
// Recursive (most common)
const recursive = new RecursiveCharacterTextSplitter({
  chunkSize: 1000,
  chunkOverlap: 200,
  separators: ["\n\n", "\n", ". ", " "],
});

// Markdown-aware splitting
import { MarkdownTextSplitter } from "langchain/text_splitter";
const markdownSplitter = new MarkdownTextSplitter({
  chunkSize: 1000,
  chunkOverlap: 100,
});
```

### The Overlap Problem

Without overlap, context at chunk boundaries is lost:

```
Chunk 1: "...the server processes the request using middleware."
Chunk 2: "The middleware validates the JWT token and extracts..."
```

If the user asks "How does the server validate JWT tokens?", neither chunk alone contains the full answer. **Overlap** ensures the boundary context exists in both chunks.

## Limitations of Naive RAG

| Problem | Description |
|---------|-------------|
| **Irrelevant retrieval** | Top-K results may not actually answer the question |
| **Lost in the middle** | LLMs pay less attention to context in the middle of long prompts |
| **No reasoning** | Simple similarity search can't handle multi-hop questions |
| **Stale embeddings** | If documents change, embeddings must be re-computed |
| **Hallucination** | The LLM may still hallucinate even with good context |

> These limitations are addressed by **Hybrid Search**, **GraphRAG**, **CRAG**, and **Self-RAG** in the following lessons.
