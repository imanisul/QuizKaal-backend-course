## 1. Introduction

**What is this lesson?**
In this lesson, we will learn how to identify users who connect to your API. We will explore the two dominant methods of authentication: **Session-based Authentication** (Stateful) and **JSON Web Tokens (JWT)** (Stateless).

**Why are we learning it?**
HTTP is a *stateless* protocol. This means every time a user sends a request to your API, the server completely forgets who they are. Without authentication, every user would have to type their password on *every single click*.

**Why should a backend engineer know this?**
Security is your primary responsibility. If you implement authentication incorrectly, hackers can forge fake sessions, steal user data, and take over admin accounts.

---

## 2. Why This Exists

**What problem existed before?**
When the web was invented, there were no "logged-in" users. It was just public documents. When Amazon tried to build the first shopping cart, they hit a massive problem: how does the server remember that *you* put the book in the cart when you navigate to the checkout page? 

**Why was this technology created?**
To solve this, Netscape invented **Cookies** in 1994. A cookie is a tiny piece of text the server gives to the browser. The browser automatically sends that cookie back to the server on every future request, saying "Hey, it's me again!"

**How did companies solve this problem?**
Companies created **Sessions**. When you log in, the server creates a unique `Session ID` (e.g., `xyz123`), saves it in its Database, and sends it to your browser as a Cookie. This worked perfectly for 20 years. But then, mobile apps and massive cloud architectures forced the invention of a new, scalable method: **JWT**.

---

## 3. Problems It Solves

**Without Sessions/JWT, APIs have amnesia.**
Imagine logging into your bank, clicking "View Balance", and the bank saying, "Who are you? Please log in again." 

**With Sessions/JWT, you stay logged in.**
Once you prove who you are (via password), the server gives you a VIP wristband (Session ID or JWT). You just show the wristband to the bouncer (the API) on every request, and they let you in instantly.

  *(The server doesn't have to remember you; the token contains your data).*

## 6. Step-by-Step Explanation

Let's break down exactly how JWT (Stateless Auth) works during a login flow:

**Step 1: The User Logs In**
↓
The user sends a `POST /login` request containing their `email` and `password`.

**Step 2: The Server Verifies**
↓
The server checks the Database. "Does this email exist? Does the password hash match?" Yes!

**Step 3: The Server Creates the JWT**
↓
The server takes the User's ID (e.g., `591`) and signs it using a secret cryptographic key (e.g., `super_secret_123`). It packages this into a JSON Web Token (JWT).

**Step 4: The Token is Sent to the Client**
↓
The server sends the JWT back to the browser (usually in an HTTP-Only Cookie or the JSON response).

**Step 5: The Client Makes a Future Request**
↓
The user clicks "View Profile". The browser sends a `GET /profile` request, attaching the JWT in the `Authorization: Bearer <token>` header.

**Step 6: The Server Verifies the JWT**
↓
The server receives the JWT. Instead of checking the Database, it uses its secret key to mathematically verify the signature. Since the signature matches, the server knows the token is authentic and extracts User ID `591`. Access Granted!

## 7. Deep Explanation: Anatomy of a JWT

A JWT is just a long string separated by two periods: `Header.Payload.Signature`. It is Base64 encoded, meaning anyone can decode and read the Payload!

<ConceptBlock type="info" title="The Three Parts of a JWT">
  **1. The Header:** Tells the server what algorithm was used to sign it (usually `HS256`).
  
  **2. The Payload:** Contains the actual data (called Claims). 
  *Example:* `{"userId": 591, "role": "admin", "exp": 1700000000}`. 
  *Warning:* Never put passwords or sensitive data in the payload, because anyone can read it!

  **3. The Signature:** The magic sauce. The server takes the Header + Payload, mixes it with a Secret Key, and creates a unique hash. If a hacker alters the Payload to say `"role": "admin"`, the Signature will no longer match, and the server will reject it!
</ConceptBlock>

## 8. Node.js Implementation

Let's build a secure login route that generates a JWT using the industry-standard `jsonwebtoken` package!

<CodeTabs>
  <div label="auth.js (Node.js)">
    ```javascript
    // 1. We import the JSON Web Token package
    const jwt = require('jsonwebtoken');

    // In production, this MUST be in your .env file!
    const JWT_SECRET = 'my_super_secret_unhackable_key_123!';

    // Fake Database User
    const dbUser = { id: 591, username: 'anisul', role: 'student' };

    console.log("--- 1. LOGGING IN ---");
    // Step 1: User provides correct password. We generate a JWT!
    const token = jwt.sign(
      { userId: dbUser.id, role: dbUser.role }, // The Payload
      JWT_SECRET,                               // The Secret Key
      { expiresIn: '1h' }                       // Token expires in 1 hour
    );

    console.log("Generated JWT Token:");
    console.log(token);
    
    console.log("\n--- 2. VERIFYING A VALID REQUEST ---");
    // Step 2: The user sends the token in a future request
    try {
      // We verify the token using the EXACT SAME secret key
      const decodedData = jwt.verify(token, JWT_SECRET);
      
      console.log("Access Granted! User Data:");
      console.log(decodedData);
      
    } catch (error) {
      console.log("Access Denied! Invalid Token.");
    }

    console.log("\n--- 3. HACKER ATTEMPT ---");
    // Step 3: A hacker tries to forge a token using a fake secret key
    const fakeToken = jwt.sign({ userId: 591, role: 'admin' }, 'wrong_secret');
    
    try {
      // Our server tries to verify it with OUR real secret key
      jwt.verify(fakeToken, JWT_SECRET);
    } catch (error) {
      console.error("🚨 HACKER BLOCKED: " + error.message);
    }
    ```
  </div>
</CodeTabs>

## 10. Common Mistakes

<WarningCard title="Putting Sensitive Data in JWTs">
  **The Mistake:** Storing a user's password, credit card, or social security number inside the JWT payload so you don't have to fetch it from the database.

  **Why it happens:** Beginners think that because the JWT has a "cryptographic signature", the payload is encrypted and hidden.

  **The Fix:** JWTs are **Signed**, not **Encrypted**. Anyone who possesses the token can base64-decode the payload and read the text instantly! Only put non-sensitive data (like User ID or Role) in the payload.
</WarningCard>

## 11. Best Practices

**How to invalidate a JWT?**
Because a JWT is stateless, the server doesn't track it. If a user clicks "Log Out", how do you destroy the token? You can't! 
If the token has a 24-hour expiration, it remains valid for 24 hours, even if the user is deleted from the database! 
**The Solution:** Set short expiration times (e.g., 15 minutes) and use a "Refresh Token" system to continuously issue new short-lived tokens.

**Where to store the JWT?**
Never store JWTs in JavaScript `localStorage`. If your frontend has an XSS (Cross-Site Scripting) vulnerability, a hacker can execute a script to steal the token from `localStorage` and hijack the account.
**The Solution:** Store the JWT in an `HttpOnly`, `Secure` Cookie. The browser handles it automatically, and JavaScript cannot read it, making it immune to XSS!

## 12. Performance & Security

**Performance (Why scale with JWT?):**
Imagine you have 10 Web Servers behind a Load Balancer. With **Sessions**, if Server A creates the session in its RAM, and the Load Balancer routes the next request to Server B, Server B will reject the user because it doesn't have the session! You would need a centralized Redis database just to share sessions.
With **JWT**, *any* server can mathematically verify the token independently, without talking to a database. This allows infinite, zero-latency horizontal scaling!

## 15. Summary

*   **Sessions** are Stateful. The server remembers you by storing your Session ID in a database.
*   **JWTs** are Stateless. The server doesn't remember you; it just mathematically verifies the signature on your token.
*   **JWT Anatomy:** Header, Payload (Data), Signature.
*   **Security:** Anyone can read the payload of a JWT. Do not store passwords in it!
*   **Scaling:** JWTs are perfect for microservices because any server can verify them instantly.
