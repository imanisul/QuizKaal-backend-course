## 1. Introduction

**What is this lesson?**
In this lesson, we will explore **Load Balancing**, the technology that allows websites to handle millions of simultaneous users without crashing. We will learn how a single IP address can secretly route traffic to 10,000 different servers.

**Why are we learning it?**
A single Node.js server can handle roughly 10,000 concurrent connections. If 1 million users visit your app during the Superbowl, your single server will catch fire. You must learn how to distribute that traffic.

**Why should a backend engineer know this?**
If you want to build high-availability architectures, you must understand Reverse Proxies, Layer 4 vs Layer 7 routing, and algorithmic traffic distribution (Round Robin, Least Connections, etc).

---

## 2. Why This Exists

**What problem existed before?**
In the early days of the internet, if `google.com` pointed to `192.168.1.50`, then 100% of the world's traffic went to that one physical computer. The only way to handle more traffic was Vertical Scaling (buying a $50,000 supercomputer). Eventually, even the biggest supercomputers melted.

**Why was this technology created?**
Engineers realized it was infinitely cheaper to buy 1,000 cheap $50 computers (Horizontal Scaling) than one $50,000 supercomputer. But how do you get 1 million users to talk to 1,000 different IP addresses?
They invented the **Load Balancer**. 

**How did companies solve this problem?**
Now, `google.com` points to a single IP address: The Load Balancer. The Load Balancer is a blazing fast, ultra-optimized server (like Nginx) that does zero computation. It just looks at the incoming request and instantly forwards it to one of the 1,000 backend servers behind it!

---

## 3. Problems It Solves

**Single Point of Failure:**
Without a Load Balancer, if your server's hard drive fails, your entire website goes offline.
With a Load Balancer, if Server #4 catches fire, the Load Balancer instantly detects it (Health Checks) and routes all future traffic to the remaining 999 servers. The user never even notices an error!

**State Exhaustion:**
A single Node.js process is single-threaded. It can only use 1 CPU core. If you run it on a 64-core machine, 63 cores sit completely idle! Load Balancing allows you to run 64 Node.js processes on the same machine and distribute the work evenly across all cores.

## 6. Step-by-Step Explanation

Let's break down the core algorithms Load Balancers use to route traffic:

**1. Round Robin**
↓
The simplest algorithm. The Load Balancer sends Request 1 to Server A, Request 2 to Server B, Request 3 to Server C, Request 4 back to Server A. It just goes in a circle. Great if all servers are identical.

**2. Least Connections**
↓
If Server A is stuck processing a massive 10GB video upload, it might be slow. The Load Balancer looks at who has the *fewest active connections* and sends the next request to Server B instead.

**3. IP Hash (Sticky Sessions)**
↓
The Load Balancer takes the User's IP address (e.g., `192.168.1.5`) and hashes it. This guarantees that User X will ALWAYS be routed to Server B. This is critical if Server B is storing the user's shopping cart in its local RAM (though you should be using Redis instead!).

**4. Health Checks**
↓
Every 5 seconds, the Load Balancer pings `/health` on all 1,000 backend servers. If Server 42 fails to respond with a `200 OK`, it is temporarily removed from the rotation until it recovers.

## 7. Deep Explanation: Layer 4 vs Layer 7

<ConceptBlock type="info" title="The OSI Model">
  **Layer 4 Load Balancing (Transport Layer):**
  The Load Balancer routes traffic purely based on the IP address and Port (TCP/UDP). It does not look at the HTTP data. It is insanely fast (handling millions of requests per second) because it doesn't decrypt HTTPS or read the headers. AWS Network Load Balancer (NLB) operates here.

  **Layer 7 Load Balancing (Application Layer):**
  The Load Balancer actually reads the HTTP request. It can see the URL! 
  If the user requests `api.myapp.com/images`, the Load Balancer routes it to the Image Servers. If they request `api.myapp.com/video`, it routes it to the Video Servers. It is slightly slower, but allows "Smart Routing". AWS Application Load Balancer (ALB) operates here.
</ConceptBlock>

## 8. Node.js Implementation

If you rent a 16-core AWS server and run `node server.js`, Node.js will only use **1 core** because it is single-threaded! 
Let's use the native Node.js `cluster` module to create our own mini-Load Balancer that spawns 16 copies of the app and distributes traffic across all cores!

<CodeTabs>
  <div label="cluster.js (The Mini Load Balancer)">
    ```javascript
    const cluster = require('cluster');
    const os = require('os');
    const express = require('express');

    // Count how many CPU cores this physical machine has
    const numCPUs = os.cpus().length;

    if (cluster.isPrimary) {
      console.log(`👑 Primary Load Balancer running (PID: ${process.pid})`);
      console.log(`💻 Spawning ${numCPUs} Worker processes...`);

      // 1. Fork a new Node.js process for every CPU core!
      for (let i = 0; i < numCPUs; i++) {
        cluster.fork();
      }

      // 2. Health Check: If a worker crashes, spawn a new one instantly!
      cluster.on('exit', (worker, code, signal) => {
        console.log(`💀 Worker ${worker.process.pid} died. Spawning replacement...`);
        cluster.fork();
      });

    } else {
      // 3. This code runs inside the Worker processes!
      const app = express();
      
      app.get('/', (req, res) => {
        // Simulate heavy CPU work
        let total = 0;
        for(let i = 0; i < 5000000; i++) total++;
        
        res.send(`✅ Handled by Worker ${process.pid}`);
      });

      // 4. ALL workers listen on the exact same port!
      // The Primary Load Balancer automatically intercepts Port 3000 
      // and distributes the incoming requests to the idle workers via Round-Robin.
      app.listen(3000, () => {
        console.log(`👷 Worker started (PID: ${process.pid})`);
      });
    }
    ```
  </div>
</CodeTabs>

**How to test this:**
Run `node cluster.js`. If your Macbook has 10 cores, you will see 10 Workers start up! Open 10 browser tabs and refresh them rapidly. You will see different PIDs responding, proving that the traffic is perfectly balanced across all your CPU cores!

## 9. Interactive Playground

Want to build a real infrastructure Load Balancer?
Create a file named `nginx.conf`:

```nginx
upstream my_backend {
    server localhost:3001;
    server localhost:3002;
    server localhost:3003;
}

server {
    listen 80;
    location / {
        proxy_pass http://my_backend;
    }
}
```
Install Nginx and run it. When you visit `localhost:80`, Nginx will silently Round-Robin your traffic to the three backend Node servers!

## 10. Common Mistakes

<WarningCard title="Stateful Servers">
  **The Mistake:** Using `express-session` to store the user's Login Token in the server's RAM.

  **Why it happens:** It works perfectly on `localhost` when you only have 1 server.

  **The Fix:** When you deploy a Load Balancer, Request 1 (Login) goes to Server A. The session is saved in Server A's RAM. 
  Request 2 (Get Profile) goes to Server B via Round-Robin. Server B checks its RAM, sees no session, and kicks the user out! 
  **Your backend servers MUST be stateless.** Move all session data to a centralized Redis cache, or use JWTs, so any server can handle any request!
</WarningCard>

## 11. Best Practices

**Auto-Scaling Groups (ASG):**
A Load Balancer by itself doesn't magically create new servers. You must pair it with an Auto-Scaling Group in AWS. 
Rule: "If the average CPU of all 5 servers goes above 80%, tell AWS to boot up 3 brand new servers and attach them to the Load Balancer." When traffic drops at night, the ASG deletes the extra servers to save money!

**SSL Termination:**
Decrypting HTTPS traffic requires heavy CPU math. Instead of forcing your 50 backend Node.js servers to do this math, you upload your SSL Certificate directly to the Load Balancer. The Load Balancer decrypts the HTTPS request, and forwards it to your Node.js servers as plain HTTP over the internal private network. This saves massive CPU overhead!

---

## 12. Performance & Security

**Security (DDoS Protection):**
Because the Load Balancer is the only server exposed to the public internet (your Node.js servers are locked in a Private Subnet), it acts as a shield. If a hacker launches a DDoS attack (sending 1 million fake requests a second), modern Load Balancers (like Cloudflare or AWS ALB) can detect the malicious IP addresses and drop the traffic at the edge, before it ever touches your fragile Node.js servers!

## 15. Summary

*   **Load Balancers** distribute traffic across multiple servers.
*   **Horizontal Scaling** is how tech giants handle millions of users.
*   **Algorithms:** Round Robin, Least Connections, IP Hash.
*   **Health Checks:** Automatically remove dead servers from the rotation.
*   **Layer 7 Routing:** Routes traffic based on the URL (e.g., `/api/users`).
*   **Node.js Cluster:** The native way to load balance across CPU cores.
