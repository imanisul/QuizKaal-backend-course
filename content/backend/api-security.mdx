## 1. Simple Explanation

Building an API is like building a bank. Authentication (checking IDs) is the front door security. However, what happens if someone inside the bank tries to open every single safety deposit box 10,000 times a second? Or what if a robber disguises themselves as a legitimate customer?
**API Security** involves setting up cameras, strict rules, and speed limits (Rate Limiting) to ensure that even authenticated users cannot abuse or crash the system, and that malicious scripts cannot impersonate real users.

## 2. Why this technology exists

In the early days of the web, security was mostly an afterthought. As APIs became the backbone of the internet, attackers realized they didn't need to guess passwords; they could just overwhelm a server with traffic (DDoS) to crash it, or trick a browser into running a malicious script that steals a user's session cookie. Modern API security mechanisms like CORS and Rate Limiting were created to mitigate these automated and sophisticated attacks.

## 3. What problem it solves

- **Rate Limiting (Throttling):** Prevents Brute Force attacks (guessing passwords), DDoS attacks, and API abuse by limiting how many requests a user or IP can make in a given timeframe.
- **CORS (Cross-Origin Resource Sharing):** Prevents malicious websites from making API requests to your server on behalf of a user.
- **XSS (Cross-Site Scripting):** Prevents attackers from injecting malicious JavaScript into your website to steal user tokens.
- **CSRF (Cross-Site Request Forgery):** Prevents attackers from tricking a logged-in user's browser into submitting a form (like transferring money) without their consent.

## 4. Real-life analogy

**Rate Limiting is like an All-You-Can-Eat Buffet.**
You pay your entry fee (Authentication) and you are allowed to eat. However, if you try to take 500 pizzas in 10 seconds, the manager (Rate Limiter) will kick you out. You are allowed to eat, but only at a reasonable human pace.

**CORS is like a strict Bouncer checking your origin.**
If you try to enter an exclusive club (The API), the bouncer asks, *"Where are you coming from?"* If you say *"MaliciousHacker.com"*, the bouncer rejects you. If you say *"MyOfficialWebsite.com"*, they let you in.

## 7. Step-by-step process explanation

**How Rate Limiting Works (Token Bucket Algorithm):**
1. A user (identified by IP or UserID) makes a request.
2. The server checks a fast cache (like Redis) for a "bucket" belonging to that user.
3. The bucket holds "tokens" (e.g., 100 tokens). Every request costs 1 token.
4. If the bucket has tokens, the server subtracts 1 and processes the request.
5. If the bucket is empty, the server rejects the request with a `429 Too Many Requests` status code.
6. The bucket slowly refills over time (e.g., 10 tokens per minute).

## 8. Code examples

**Express.js Rate Limiting (using `express-rate-limit`):**
```javascript
const rateLimit = require('express-rate-limit');
const express = require('express');
const app = express();

// Apply a limit to all requests
const globalLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 100, // Limit each IP to 100 requests per `window`
  message: 'Too many requests from this IP, please try again after 15 minutes',
  standardHeaders: true, // Return rate limit info in the `RateLimit-*` headers
});

app.use(globalLimiter);

// Stricter limit for login to prevent brute force
const loginLimiter = rateLimit({
  windowMs: 60 * 1000, // 1 minute
  max: 5, // Only 5 login attempts per minute per IP
});

app.post('/api/login', loginLimiter, (req, res) => {
  // login logic...
});
```

**Express.js CORS setup:**
```javascript
const cors = require('cors');

const corsOptions = {
  origin: 'https://my-official-frontend.com',
  optionsSuccessStatus: 200,
  credentials: true // Allow cookies to be sent!
};

app.use(cors(corsOptions));
```

## 9. Common Use Cases

- **Brute Force Protection:** Applying strict rate limits to `/login` or `/forgot-password` routes.
- **API Monetization:** Giving free users 100 requests/day, and paying users 10,000 requests/day (checking User ID instead of IP).
- **CORS for Public APIs:** If you are building a public API like Stripe or Twilio, you might set `origin: '*'` to allow anyone to use it. If it's your private backend, you restrict it strictly to your frontend domain.

## 10. Best practices

- **Use Redis for Rate Limiting:** Storing rate limit counters in a standard SQL database is too slow. Use Redis because it handles rapid incrementing effortlessly.
- **Set Security Headers:** Always use a library like `helmet` in Express to automatically set HTTP headers (like CSP, X-Frame-Options) that protect against XSS and Clickjacking.
- **Sanitize Input:** Never trust user input. Always use validation libraries (like Joi or Zod) to strip out malicious SQL or JavaScript before saving to the database.

## 11. Common mistakes

- **Relying entirely on IP addresses for Rate Limiting:** If 50 students are in a university library, they all share the same public IP. If one student spams your API, the other 49 will be blocked too! For authenticated routes, rate limit by `User ID`, not `IP`.
- **Setting CORS to `*` with Credentials:** Browsers will outright reject a request if you set `Access-Control-Allow-Origin: *` AND `Access-Control-Allow-Credentials: true`. You must specify the exact origin if you want to allow cookies.
- **Returning verbose error messages:** Never return detailed stack traces or database errors (e.g., "Table users doesn't exist") to the client. It gives attackers a map of your internal architecture.

## 12. Performance tips

- **API Gateway:** Instead of running the Rate Limiter inside your Node.js application, offload it to an API Gateway (like Nginx, AWS API Gateway, or Cloudflare). This prevents malicious traffic from even reaching your Node server, saving massive CPU cycles.

## 13. Security considerations

- **CSRF Tokens:** If you use Cookie-based authentication, an attacker can trick a user into clicking a link that triggers a state-changing POST request to your API. You must either use `SameSite=Strict` cookies, or require a unique CSRF token in the header of every POST/PUT/DELETE request.
- **XSS Mitigation:** To prevent XSS, always escape user-generated content before rendering it in the browser (React does this automatically!). Also, implement a strict **Content Security Policy (CSP)** to prevent the browser from executing unauthorized inline scripts.

## 14. Scalability & Deployment

- If you have 5 Node.js servers behind a load balancer, and you use in-memory rate limiting (like standard `express-rate-limit`), a user can make 100 requests to Server A, then 100 requests to Server B. You MUST use a centralized Redis store (e.g., `rate-limit-redis`) so all servers share the same counter.

## 15. Interview questions

**Q: What is the difference between XSS and CSRF?**
A: **XSS (Cross-Site Scripting)** is when an attacker injects malicious JavaScript into your website, which runs in the victim's browser and steals their data. **CSRF (Cross-Site Request Forgery)** is when an attacker tricks the victim's browser into making an unwanted, authenticated request to your server (e.g., forcing them to transfer money while they are logged into the bank in another tab).

**Q: How does CORS work under the hood?**
A: When a browser makes a cross-origin request (like from `domain-a.com` to `api-b.com`), it first sends an HTTP `OPTIONS` request (a "Preflight" request). The server responds with headers indicating which origins and methods are allowed. If `domain-a.com` isn't on the list, the browser blocks the actual request.

**Q: What HTTP status code is used for Rate Limiting?**
A: `429 Too Many Requests`.

   - A) CORS

## 18. Summary

API Security is a multi-layered defense system. You use CORS to ensure only trusted domains can talk to you, Helmet/CSP to protect users from XSS, CSRF tokens to ensure requests are intentional, and robust Rate Limiting backed by Redis to protect your infrastructure from being overwhelmed. Security is not a feature you add at the end; it must be baked into the architecture from day one.
