## 1. Introduction

**What is this lesson?**
In this lesson, we will learn about **GraphQL**—a query language for your API that allows the frontend to ask for exactly what it needs, and nothing more.

**Why are we learning it?**
While REST is the industry standard, it forces the frontend to adapt to whatever shape the backend decides to send. GraphQL flips this dynamic, putting the power in the hands of the frontend developer to request custom-tailored data structures.

**Why should a backend engineer know this?**
Many modern tech companies (Facebook, GitHub, Shopify, Netflix) have migrated heavily to GraphQL. If you only know REST, you are missing out on half of modern API architecture.

---

## 2. Why This Exists

**What problem existed before?**
With REST APIs, you suffer from two massive problems:
1. **Over-fetching:** The frontend needs a user's `name` to display in the header. It calls `GET /users/1`. The REST API returns the name, but also the user's `email`, `password_hash`, `address`, `phone_number`, and `date_of_birth`. You wasted bandwidth downloading 50 unused fields just to get 1 name.
2. **Under-fetching:** To load a profile page, the frontend needs the User's data, their 5 most recent Posts, and the Comments on those Posts. In REST, the frontend has to make 3 separate HTTP requests (`/users/1`, then `/users/1/posts`, then `/posts/1/comments`). This makes mobile apps incredibly slow.

**Why was this technology created?**
In 2012, Facebook was rebuilding its iOS app. Mobile networks (like 3G) were painfully slow, and making 5 different REST API calls to load the Facebook News Feed was causing the app to freeze. They invented GraphQL to solve this.

**How did companies solve this problem?**
Instead of having hundreds of REST endpoints (`/users`, `/posts`, `/comments`), GraphQL uses a **single endpoint** (usually `POST /graphql`). The frontend sends a JSON document describing the exact shape of the data it wants, and the backend returns exactly that shape in a single network request.

---

## 3. Problems It Solves

**Without GraphQL, frontend and backend teams fight constantly.**
Frontend: *"Can you add the user's profile picture URL to the `/posts` endpoint? We need it for the UI."*
Backend: *"No, that breaks the REST structure. Just make a second API call."*

**With GraphQL, frontend developers are independent.**
Because the backend exposes a massive "Graph" of all possible data, the frontend developer can query the `profilePicture` field themselves without ever asking the backend engineer to write new code!

## 6. Step-by-Step Explanation

Let's break down the three core pillars of a GraphQL architecture:

**Step 1: The Schema (Type Definitions)**
↓
The backend engineer writes a strict contract (Schema) that defines exactly what data exists.
```graphql
type User {
  id: ID!
  name: String!
  email: String
  posts: [Post]
}
```

**Step 2: The Query (What the Frontend Asks For)**
↓
The frontend developer writes a Query asking for specific fields based on the Schema.
```graphql
query {
  user(id: "1") {
    name
    posts {
      title
    }
  }
}
```

**Step 3: The Resolvers (How the Backend gets the Data)**
↓
The backend engineer writes JavaScript functions called **Resolvers**. Every single field in the Schema has a Resolver function. When the frontend asks for `user.name`, the GraphQL engine executes the `user` resolver, then executes the `name` resolver!

---

## 7. Deep Explanation: Mutations & Subscriptions

GraphQL isn't just for reading data (Queries).

<ConceptBlock type="info" title="Mutations & Subscriptions">
  **Mutations (Replacing POST/PUT/DELETE)**
  When you want to modify data (like creating a new user or liking a post), you use a Mutation. It looks exactly like a Query, but tells the server to perform an action before returning the requested data.

  **Subscriptions (Real-time WebSockets)**
  GraphQL has built-in support for real-time data! A Subscription keeps a persistent WebSocket connection open. If you subscribe to `newMessage`, the server will automatically push new messages to the frontend the millisecond they are saved in the database!
</ConceptBlock>

## 8. Node.js Implementation

Let's build a fully functioning GraphQL API in Node.js using `@apollo/server`. We will define our Schema (TypeDefs) and our Resolvers to return a User and their Posts.

<CodeTabs>
  <div label="graphql-server.js (Node.js)">
    ```javascript
    const { ApolloServer } = require('@apollo/server');
    const { startStandaloneServer } = require('@apollo/server/standalone');

    // 1. The Schema (TypeDefs)
    // We define the exact structure of our Data and our Queries
    const typeDefs = `#graphql
      type Post {
        id: ID!
        title: String!
      }

      type User {
        id: ID!
        name: String!
        email: String!
        posts: [Post!]!
      }

      # The Query type defines the entry points into our API
      type Query {
        getUser(id: ID!): User
      }
    `;

    // Fake Database
    const usersDB = [{ id: '1', name: 'Anisul', email: 'anisul@example.com' }];
    const postsDB = [{ id: '101', userId: '1', title: 'GraphQL is awesome!' }];

    // 2. The Resolvers
    // These functions actually fetch the data from the database
    const resolvers = {
      Query: {
        // When the frontend asks for getUser, this runs:
        getUser: (_, args) => {
          return usersDB.find(user => user.id === args.id);
        },
      },
      User: {
        // This is the magic of GraphQL! If the frontend asks for `posts` inside a User,
        // this resolver runs automatically, receiving the parent User object!
        posts: (parentUser) => {
          return postsDB.filter(post => post.userId === parentUser.id);
        }
      }
    };

    // 3. Start the Server
    async function startServer() {
      const server = new ApolloServer({ typeDefs, resolvers });
      const { url } = await startStandaloneServer(server, { listen: { port: 4000 } });
      console.log(`🚀 GraphQL Server ready at ${url}`);
    }

    startServer();
    ```
  </div>
</CodeTabs>

**Expected Frontend Request:**
```graphql
# The frontend sends this Query
query {
  getUser(id: "1") {
    name
    posts {
      title
    }
  }
}
```

**Expected JSON Response:**
```json
{
  "data": {
    "getUser": {
      "name": "Anisul",
      "posts": [
        { "title": "GraphQL is awesome!" }
      ]
    }
  }
}
```

## 9. Interactive Playground

One of the greatest features of GraphQL is that it is **Introspective**. This means the GraphQL server can describe itself! 

Because of this, tools like **Apollo Studio** or **GraphiQL** give you a beautiful UI where you can explore the entire API, see the documentation, and auto-complete your queries!

If you were to run the Node.js code above and open `http://localhost:4000` in your browser, you would immediately see a Sandbox UI where you could click buttons to generate your queries!

## 10. Common Mistakes

<WarningCard title="The N+1 Query Problem">
  **The Mistake:** You query for a list of 50 Users, and for each User, you query their Posts. Your GraphQL server makes 1 database query to get the Users, and then **50 separate database queries** to get the Posts for each user.

  **Why it happens:** Because Resolvers execute independently for every single field! 1 query + 50 sub-queries = the famous N+1 problem.

  **The Fix:** Backend engineers use a tool called **DataLoader**. DataLoader intercepts all 50 independent requests for posts, batches them together, and makes a single highly-optimized `SELECT * FROM posts WHERE userId IN (1, 2, ..., 50)` query to the database!
</WarningCard>

## 11. Best Practices

**How Netflix & Amazon build this:**
Enterprise companies don't just have one GraphQL server. They use **Apollo Federation**. 
The Payments Team builds a GraphQL server for payments. The Users Team builds a GraphQL server for users. An **API Gateway** automatically merges them together into one massive "Supergraph". The frontend makes one query, and the Gateway splits the query up, routes it to the different microservices, and stitches the JSON response back together!

## 12. Performance & Security

**Performance (Caching Challenges):**
REST APIs are very easy to cache at the CDN layer because the URL is unique (e.g. `GET /users/1`). GraphQL is incredibly difficult to cache because *every* request is a `POST` to `/graphql` with a slightly different body. Companies have to use advanced tools like Apollo Router to cache individual fields.

**Security (Query Depth Limiting):**
Because GraphQL allows nested queries, a hacker could send a query like: `User -> Posts -> Comments -> Author (User) -> Posts -> Comments` looping infinitely until your server runs out of RAM and crashes! Backend engineers must implement **Query Depth Limiting** (e.g., rejecting any query nested deeper than 5 levels).

## 15. Summary

*   **GraphQL** solves the Over-fetching and Under-fetching problems of REST.
*   It operates on a single endpoint (usually `POST /graphql`).
*   **Schema:** The strict definition of available Types and Fields.
*   **Query:** The frontend asking for exactly what it wants.
*   **Resolvers:** The backend functions that fetch the requested data.
*   **Mutations:** Used to modify data (Create, Update, Delete).
