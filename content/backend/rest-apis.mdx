## 1. Introduction

**What is this lesson?**
In this lesson, we will learn about **REST** (Representational State Transfer)—the global standard for designing APIs. You will learn how to structure URLs, use HTTP Verbs correctly, and build APIs that other developers love using.

**Why are we learning it?**
An API (Application Programming Interface) is how the frontend talks to the backend. If your API is designed poorly, the frontend developers will hate you, the code will be buggy, and scaling will be a nightmare.

**Why should a backend engineer know this?**
As a backend engineer, 80% of your job is building APIs. Understanding REST is as fundamental to a backend engineer as understanding HTML is to a frontend developer.

---

## 2. Why This Exists

**What problem existed before?**
Before REST, developers used complex, heavy protocols like SOAP and XML-RPC. Every company designed their URLs and data structures differently. 
One company might use `/createNewUserRecord` while another used `/addUser`. To update a user, one might use `/editUser?id=5` while another used `/updateUserRecord_5`. It was absolute chaos.

**Why was this technology created?**
In 2000, a computer scientist named Roy Fielding introduced REST in his PhD dissertation. He proposed a standardized, predictable, and stateless way to build APIs using the exact same rules that power the World Wide Web.

**How did companies solve this problem?**
The industry rapidly adopted REST. Instead of inventing custom URL names, everyone agreed to use **Nouns** (for the URL) and **Verbs** (HTTP methods like GET, POST) to perform actions.

---

## 3. Problems It Solves

**Without REST, APIs are unpredictable.**
If you have to read a 100-page manual just to figure out what the URL is for deleting a user, the API is broken. 

**With REST, APIs are intuitive.**
If a REST API manages "Books", any developer instantly knows:
- `GET /books` (Fetches all books)
- `POST /books` (Creates a new book)
- `DELETE /books/5` (Deletes book #5)
You don't even need a manual to guess how it works!

## 4. Real Life Analogy

<AnalogyCard title="The Restaurant Menu">
  Think of a REST API like ordering food at a restaurant.

  **The Resource (Noun):** The food item (e.g., a `Burger`).
  **The HTTP Verb (Action):** What you want to do with it.

  - `GET /burger` = "Can I see the burger on the menu?"
  - `POST /burger` = "I would like to order a new burger."
  - `PUT /burger/1` = "Can you completely replace my burger with a chicken sandwich?"
  - `PATCH /burger/1` = "Can you just add extra cheese to my existing burger?"
  - `DELETE /burger/1` = "I want to cancel my burger order!"

  The waiter (the API) understands exactly what you want based on the *Noun* (Burger) and the *Verb* (Action).
</AnalogyCard>

## 6. Step-by-Step Explanation

Let's break down the core rules of a perfect REST API:

**Step 1: Base URL**
↓
Every API needs a home. Usually, it is a subdomain or a specific path.
Example: `https://api.quizkaal.com/v1/`

**Step 2: Use Plural Nouns**
↓
URLs should represent "Resources" (things), not actions. Always use plural nouns.
❌ BAD: `/getUser` or `/createPost`
✅ GOOD: `/users` or `/posts`

**Step 3: Use HTTP Methods for Actions**
↓
Instead of putting verbs in the URL, use HTTP methods.
- **GET:** Read data.
- **POST:** Create new data.
- **PUT:** Completely replace existing data.
- **PATCH:** Partially update existing data.
- **DELETE:** Remove data.

**Step 4: Use Path Parameters for Specific Items**
↓
If you want to act on a *specific* user, pass their ID in the URL path.
✅ GOOD: `GET /users/123` (Get user with ID 123)
✅ GOOD: `DELETE /users/123` (Delete user with ID 123)

**Step 5: Nesting Relationships**
↓
If a resource belongs to another resource, nest them logically!
✅ GOOD: `GET /users/123/posts` (Get all posts belonging to User 123)
✅ GOOD: `POST /users/123/posts` (Create a new post for User 123)

## 7. Deep Explanation: Status Codes

When a REST API responds, it must include an **HTTP Status Code**. This tells the frontend exactly what happened without them having to parse the JSON response.

<ConceptBlock type="info" title="Important REST Status Codes">
  **2xx (Success)**
  - `200 OK`: Request succeeded (used for GET/PUT/PATCH).
  - `201 Created`: Successfully created a new resource (used for POST).
  - `204 No Content`: Action succeeded, but there is no data to return (often used for DELETE).

  **4xx (Client Error - The Frontend messed up)**
  - `400 Bad Request`: Missing data or invalid JSON.
  - `401 Unauthorized`: Not logged in (missing token).
  - `403 Forbidden`: Logged in, but not allowed to do this.
  - `404 Not Found`: The resource doesn't exist.

  **5xx (Server Error - You messed up)**
  - `500 Internal Server Error`: Your backend code crashed.
</ConceptBlock>

## 8. Node.js Implementation

Let's build a perfectly structured REST API in Node.js using Express. We will build a simple CRUD (Create, Read, Update, Delete) API for managing "Books".

<CodeTabs>
  <div label="server.js (Node.js)">
    ```javascript
    const express = require('express');
    const app = express();

    // Middleware to parse incoming JSON data from the frontend
    app.use(express.json());

    // Fake Database
    let books = [
      { id: 1, title: 'Atomic Habits', author: 'James Clear' },
      { id: 2, title: 'Deep Work', author: 'Cal Newport' }
    ];

    // 1. GET /books (Fetch all books)
    app.get('/books', (req, res) => {
      // 200 OK
      res.status(200).json(books);
    });

    // 2. GET /books/:id (Fetch a specific book)
    app.get('/books/:id', (req, res) => {
      const bookId = parseInt(req.params.id);
      const book = books.find(b => b.id === bookId);

      if (!book) {
        // 404 Not Found
        return res.status(404).json({ error: 'Book not found' });
      }
      res.status(200).json(book);
    });

    // 3. POST /books (Create a new book)
    app.post('/books', (req, res) => {
      const { title, author } = req.body;
      
      if (!title || !author) {
        // 400 Bad Request
        return res.status(400).json({ error: 'Title and author are required' });
      }

      const newBook = { id: books.length + 1, title, author };
      books.push(newBook);
      
      // 201 Created
      res.status(201).json(newBook);
    });

    // 4. DELETE /books/:id (Delete a book)
    app.delete('/books/:id', (req, res) => {
      const bookId = parseInt(req.params.id);
      const initialLength = books.length;
      books = books.filter(b => b.id !== bookId);

      if (books.length === initialLength) {
        return res.status(404).json({ error: 'Book not found' });
      }

      // 204 No Content (Successful delete)
      res.status(204).send();
    });

    app.listen(3000, () => console.log('REST API running on Port 3000'));
    ```
  </div>
</CodeTabs>

**Expected Output (Using Postman or cURL):**
```bash
# Making a POST request
curl -X POST http://localhost:3000/books \
-H "Content-Type: application/json" \
-d '{"title": "Clean Code", "author": "Robert C. Martin"}'

# Response:
{
  "id": 3,
  "title": "Clean Code",
  "author": "Robert C. Martin"
}
```

## 10. Common Mistakes

<WarningCard title="Putting Verbs in the URL">
  **The Mistake:** Designing URLs like `POST /api/createNewUser` or `POST /api/deleteUser?id=5`.

  **Why it happens:** Beginners think of URLs as function names.

  **The Fix:** Use Nouns and HTTP methods. It should simply be `POST /api/users` to create, and `DELETE /api/users/5` to delete. The HTTP method *is* the verb!
</WarningCard>

## 11. Best Practices

**Versioning your APIs:**
When companies like Stripe or GitHub build APIs, they know they can never break existing code. Always prefix your routes with a version number like `/api/v1/users`. If you ever need to completely change how the API works, you launch `/api/v2/users` and leave `v1` running for old clients!

**Pagination, Filtering, and Sorting:**
If you have 1 million users, `GET /users` will crash your server. Use Query Parameters (`?`) to filter and paginate data.
✅ GOOD: `GET /users?role=admin&limit=20&page=2`

---

## 12. Performance & Security

**Performance (Statelessness):**
A core rule of REST is that the server must be **Stateless**. The server should *never* store a user's session in its RAM. Every single request from the client must contain all the information necessary to authenticate it (like a JWT Token). This allows you to infinitely horizontally scale your API servers!

**Security (Idempotency):**
`PUT` and `DELETE` methods must be **Idempotent**. This means if the frontend accidentally sends the exact same `DELETE /users/5` request 100 times in a row, the outcome must be exactly the same as sending it once (the user is deleted, and the database doesn't crash or throw weird errors).

## 15. Summary

*   **REST** uses standardized **HTTP Methods** (GET, POST, PUT, DELETE) to perform actions.
*   URLs must use **Plural Nouns** (`/users`), never verbs (`/getUser`).
*   **Path Parameters** identify specific resources (`/users/123`).
*   **Query Parameters** filter and paginate (`/users?role=admin`).
*   Always return the correct **HTTP Status Code** (200, 201, 400, 404).
