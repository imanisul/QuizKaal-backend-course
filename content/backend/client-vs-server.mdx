## 1. The Core Architecture

<ConceptBlock type="idea" title="Overview">
  Every modern web application is divided into two distinct halves that talk to each other over the internet. The Client asks for data, and the Server processes the request and provides the data.
</ConceptBlock>

<AnalogyCard title="The Restaurant Analogy">
  The Client-Server model is exactly like dining at a restaurant. 
  - **You (The Client):** Look at the menu and place an order.
  - **The Kitchen (The Server):** Receives the order, prepares the food (data) according to business logic, and makes sure you get what you asked for.
  - **The Waiter (The Network/API):** Transports the order to the kitchen and brings the food back to you.
</AnalogyCard>

## 4. Why Not Just One Computer?

Why do we separate the Client and the Server? Why doesn't your phone just store all of Netflix's movies and run all the logic?

1. **Storage:** Netflix has petabytes of video data. Your phone has 128GB of storage.
2. **Security:** If your phone talked directly to the database, hackers could easily steal other users' data. The Server acts as a bouncer, enforcing authentication.
3. **Compute Power:** Running heavy AI models or processing millions of transactions requires massive CPU power that a phone battery cannot support.

## 5. Node.js Implementation: Express Server

Let's look at exactly how a Server (backend) and a Client (frontend) interact using Node.js and Express.

<CodeTabs>
  <div label="server.js (Backend)">
    ```javascript
    // 1. Import Express (The most popular Node.js web framework)
    const express = require('express');
    const app = express();

    // 2. Define a "Route" (The Waiter taking an order)
    // When the Client asks for '/api/menu', the Server runs this function
    app.get('/api/menu', (req, res) => {
      
      // 3. The Server fetches data (Pretend this comes from a Database)
      const data = {
        item: "Margherita Pizza",
        price: 12.99,
        inStock: true
      };

      // 4. The Server sends the data back to the Client as JSON
      res.json(data);
    });

    // 5. Start the Server on port 3000
    app.listen(3000, () => {
      console.log("🍳 Kitchen (Server) is open on port 3000");
    });
    ```
  </div>
  <div label="app.js (Frontend)">
    ```javascript
    // 1. The Client (Browser) places an order to the Server
    console.log("Placing order...");

    fetch('http://localhost:3000/api/menu')
      .then(response => response.json()) // 2. Wait for the Server to reply
      .then(data => {
        // 3. Display the food (data) to the user!
        console.log(`The server replied: We have ${data.item} for $${data.price}`);
      })
      .catch(error => console.error("The server is down!", error));
    ```
  </div>
</CodeTabs>

<ConceptBlock type="tip" title="Notice the separation?">
  The frontend code (`app.js`) has absolutely no idea *how* the pizza was made, or what database it came from. It simply asks the URL for data and trusts the Server to handle the complex logic.
</ConceptBlock>

## 6. Real World Practice

<PracticeExercise title="Identify the Client and Server">
  Think about applications in your daily life:
  - When you play a multiplayer game like *Fortnite*, what is the Client? (Your PS5/PC). What is the Server? (Epic Games' data centers).
  - When you use Spotify offline, are you using a Client-Server model? (No, until it needs to sync data or stream a new song!)
  
  *Hint: If you turn on Airplane Mode and an app stops working, it relies heavily on a Server!*
