## 1. Introduction

**What is this lesson?**
In this lesson, we will explore **Microservices Architecture**. Instead of building one massive application, you build 50 tiny applications that communicate with each other over a network. 

**Why are we learning it?**
Netflix, Uber, and Amazon do not have a single `server.js` file running their entire company. They have thousands of individual microservices. You must understand how to break a Monolith apart to scale a massive engineering organization.

**Why should a backend engineer know this?**
"How would you design Uber?" is a classic System Design interview question. You must be able to architect a system where the Ride Matching Service, the Billing Service, and the Notification Service are completely independent.

---

## 2. Why This Exists

**What problem existed before?**
As a startup becomes a unicorn, the Monolith becomes a nightmare. If you have 500 developers committing code to one repo, they constantly break each other's code. Deploying the massive Monolith takes 45 minutes, so deployments only happen once a month.

**Why was this technology created?**
Microservices were created to solve **Organizational Scaling**. By splitting the app into tiny services, the "Billing Team" (5 developers) gets their own repository, their own database, and their own server. They can deploy their Billing Service 10 times a day without ever talking to the "User Team"!

**How did companies solve this problem?**
Companies like Amazon pioneered the "Two-Pizza Team" rule. A team should be small enough to be fed by two pizzas. Each team completely owns, builds, and deploys one specific Microservice.

---

## 3. Problems It Solves

**Monoliths: A single point of failure.**
If the code that generates PDF reports has a memory leak, it crashes the entire Monolith, taking down the Login page, the Checkout page, and the Homepage.

**Microservices: Isolated failures (Blast Radius).**
If the PDF Report Microservice crashes, it only affects PDF generation. The rest of the platform (Login, Checkout) continues running perfectly because they are hosted on entirely different servers!

## 4. Real Life Analogy

<AnalogyCard title="The Swiss Army Knife vs The Toolbox">
  **The Monolith (Swiss Army Knife):**
  A Swiss Army Knife has a blade, a screwdriver, and scissors all physically attached to one handle. It is incredibly convenient. However, if the scissors break, you have to send the *entire* knife back to the factory to be repaired.

  **Microservices (The Toolbox):**
  A Toolbox contains 50 separate, specialized tools. If the scissors break, you throw them away and buy new scissors. The rest of the tools are completely unaffected. But, carrying a massive toolbox requires management and organization!
</AnalogyCard>

## 6. Step-by-Step Explanation

Let's break down the core components of a Microservices Architecture:

**1. Independent Databases**
↓
This is the golden rule: **Microservices must not share a database**. The User Service has a Postgres DB. The Billing Service has a MongoDB DB. The User Service is physically not allowed to query the Billing DB. It MUST make an HTTP request to the Billing Service's API to ask for the data.

**2. The API Gateway**
↓
If you have 50 microservices, a mobile app shouldn't have to memorize 50 different IP addresses to fetch data. You place an **API Gateway** in front of them. The mobile app makes *one* request to `api.myapp.com/checkout`, and the Gateway internally routes it to the correct microservice.

**3. Service Discovery**
↓
Because microservices dynamically scale up and down, their IP addresses change constantly. **Service Discovery** (like Consul or Kubernetes CoreDNS) is a dynamic phonebook. The API Gateway asks the phonebook, "What is the current IP address of the Billing Service?" before routing the request.

## 7. Deep Explanation: The Distributed Data Problem

<ConceptBlock type="info" title="The Nightmare of Eventual Consistency">
  In a Monolith, if a user deletes their account, you use a SQL Transaction to instantly delete them from the Users table AND the Billing table.
  
  In Microservices, the databases are split! 
  The User Service deletes the user from Postgres, but how does the Billing Service know to delete their credit card from MongoDB?
  
  **The Solution:** The User Service deletes the user, and then publishes a `"USER_DELETED"` event to a Message Queue (like RabbitMQ or Kafka). The Billing Service listens for this event and eventually deletes the credit card. 
  This is called **Eventual Consistency**. It is incredibly difficult to debug and is the #1 reason why you shouldn't use Microservices unless absolutely necessary!
</ConceptBlock>

## 8. Node.js Implementation

Let's build a simple **API Gateway** using Express and `http-proxy-middleware` that routes traffic to two different Microservices running on different ports!

<CodeTabs>
  <div label="gateway.js (The API Gateway)">
    ```javascript
    const express = require('express');
    const { createProxyMiddleware } = require('http-proxy-middleware');

    const app = express();

    // The Gateway intercepts the request and proxies it to the correct Microservice!
    app.use('/users', createProxyMiddleware({ 
      target: 'http://localhost:3001', 
      changeOrigin: true 
    }));

    app.use('/billing', createProxyMiddleware({ 
      target: 'http://localhost:3002', 
      changeOrigin: true 
    }));

    app.listen(3000, () => {
      console.log('🚪 API Gateway listening on Port 3000');
    });
    ```
  </div>
  <div label="user-service.js (Microservice 1)">
    ```javascript
    const express = require('express');
    const app = express();

    app.get('/users/profile', (req, res) => {
      res.json({ id: 1, name: "Anisul", role: "Engineer" });
    });

    app.listen(3001, () => {
      console.log('👤 User Service running on Port 3001');
    });
    ```
  </div>
  <div label="billing-service.js (Microservice 2)">
    ```javascript
    const express = require('express');
    const app = express();

    app.get('/billing/invoices', (req, res) => {
      res.json([{ id: 999, amount: 50.00, status: "paid" }]);
    });

    app.listen(3002, () => {
      console.log('💳 Billing Service running on Port 3002');
    });
    ```
  </div>
</CodeTabs>

**How to test this:**
1. Run all 3 files in separate terminals.
2. Hit `GET http://localhost:3000/users/profile`. The Gateway routes it to Port 3001!
3. Hit `GET http://localhost:3000/billing/invoices`. The Gateway routes it to Port 3002!
The client only ever talks to Port 3000!

## 10. Common Mistakes

<WarningCard title="The Distributed Monolith">
  **The Mistake:** Splitting code into 10 microservices, but they all still connect to the exact same shared PostgreSQL database.

  **Why it happens:** Developers want the "coolness" of microservices without doing the incredibly hard work of decoupling the database schemas.

  **The Fix:** This is an anti-pattern called a Distributed Monolith. If the shared database goes down, all 10 microservices crash simultaneously. Furthermore, if Team A renames a column, Team B's microservice instantly breaks. You MUST split the database!
</WarningCard>

---

## 11. Best Practices

**Circuit Breakers:**
In a Monolith, a function call rarely fails. In Microservices, network calls fail constantly. If the User Service calls the Billing Service, and the Billing Service is timing out, the User Service will wait 30 seconds, eventually running out of memory. 
You must use a **Circuit Breaker** (like the `opossum` package in Node.js). If the Billing Service fails 5 times in a row, the Circuit "Trips" (opens) and instantly returns a fallback error for the next 60 seconds, giving the Billing Service time to recover!

**Centralized Logging:**
If a request flows through the Gateway -> User Service -> Inventory Service -> Billing Service, and it crashes, how do you know which server caused the bug? You must implement **Distributed Tracing** (using tools like Jaeger or Datadog) to trace a single request ID across multiple servers!

---

## 12. Performance & Security

**Performance (Network Latency):**
Microservices are inherently slower than Monoliths. Serializing JSON, sending it over TCP, and deserializing it adds milliseconds to every internal hop. To optimize this, high-performance microservices communicate using **gRPC and Protocol Buffers** instead of HTTP/JSON. gRPC sends binary data, which is 10x faster and uses less bandwidth.

## 15. Summary

*   **Microservices** split an app into independent, network-connected services.
*   **API Gateway:** The front door that routes traffic.
*   **Database-per-Service:** Never share a database between microservices.
*   **Circuit Breakers:** Prevent cascading failures when a network request times out.
*   **Blast Radius:** Microservices isolate crashes to a single feature.
