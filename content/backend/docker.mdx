## 1. Introduction

**What is this lesson?**
In this lesson, we will learn about **Docker**, the industry standard for Containerization. It is a tool that allows you to package your application, its dependencies, and the entire operating system into a single, portable box called a Container.

**Why are we learning it?**
If you want to deploy a Microservices Architecture with 50 Node.js servers, you cannot manually SSH into 50 Linux machines to install `node v18` and `npm install`. Docker allows you to write a single text file that automatically builds and runs your app anywhere in the world, identically.

**Why should a backend engineer know this?**
"It works on my machine, but it crashes on the production server." Every engineer has said this. Docker completely eliminates this problem. If your code runs inside a Docker container on your Macbook, it is 100% guaranteed to run exactly the same way on AWS.

---

## 2. Why This Exists

**What problem existed before?**
Before Docker, companies used **Virtual Machines (VMs)** to isolate applications. If you wanted to run 3 isolated Node.js apps on a physical server, you had to install 3 entire Virtual Operating Systems (like Ubuntu). Each VM took up 20GB of hard drive space and 4GB of RAM just to boot the OS, leaving almost no resources for your actual code!

**Why was this technology created?**
Docker (released in 2013) introduced Linux Containers to the masses. Instead of virtualizing the hardware to run multiple OSs, Docker virtualizes the *Operating System itself*. 

**How did companies solve this problem?**
With Docker, all 3 Node.js apps share the exact same underlying Linux kernel, but they *think* they are isolated. A Docker Container takes up 50 Megabytes (instead of 20 Gigabytes) and boots up in 0.1 seconds (instead of 2 minutes). You can run thousands of containers on a single machine!

---

## 3. Problems It Solves

**The Dependency Matrix from Hell:**
App A requires Node.js v14. App B requires Node.js v18. If you try to run both on the same laptop, they conflict and crash. 
Docker puts App A inside a sealed box with Node v14, and App B inside a sealed box with Node v18. They never see each other.

**The Onboarding Nightmare:**
When a new developer joins the company, they spend 3 days installing PostgreSQL, Redis, Node, Python, and setting up environment variables just to run the app locally.
With Docker, they type exactly one command: `docker-compose up`. The entire massive architecture boots up on their laptop in 30 seconds.

## 6. Step-by-Step Explanation

Let's break down the core terminology of Docker:

**1. The Dockerfile**
↓
A simple text file containing the exact instructions on how to build your app. ("Start with Ubuntu, install Node, copy my code, run npm install").

**2. The Docker Image**
↓
When you "Build" the Dockerfile, Docker executes the instructions and freezes the result into a read-only template called an **Image**. An Image is like a Class in Object-Oriented Programming, or a blueprint for a house.

**3. The Docker Container**
↓
When you "Run" the Image, it becomes a **Container**. A Container is the actual live, running process. You can spawn 100 running Containers (Houses) from a single Image (Blueprint).

**4. Docker Hub / Registry**
↓
Once you build an Image, you upload it to a Registry (like Docker Hub or AWS ECR). This is just like pushing code to GitHub. Your production server then downloads the Image and runs it!

## 7. Deep Explanation: Image Layers

<ConceptBlock type="info" title="Why is Docker so fast?">
  When you build a Dockerfile, every single line creates a new "Layer" on the hard drive. 
  
  Line 1: `FROM node:18` (Downloads 100MB Node OS) -> Layer A
  Line 2: `COPY package.json .` (Copies 1KB file) -> Layer B
  Line 3: `RUN npm install` (Downloads 50MB node_modules) -> Layer C
  Line 4: `COPY src/ ./src` (Copies your code) -> Layer D
  
  If you change a typo in your Javascript code (Layer D) and rebuild the image, Docker is incredibly smart. It realizes Layers A, B, and C haven't changed! It completely skips them, using the cached layers. It only rebuilds Layer D, which takes 0.1 seconds!
</ConceptBlock>

## 8. Node.js Implementation

Let's look at the absolute gold-standard `Dockerfile` for a production Node.js application, and how to run it.

<CodeTabs>
  <div label="Dockerfile">
    ```dockerfile
    # 1. Use the official, lightweight Alpine Linux version of Node 18
    FROM node:18-alpine

    # 2. Set the working directory inside the container
    WORKDIR /usr/src/app

    # 3. Copy ONLY package files first (to heavily optimize Docker Caching)
    COPY package*.json ./

    # 4. Install dependencies (This layer gets cached unless package.json changes!)
    RUN npm ci --only=production

    # 5. Copy the rest of the application code
    COPY . .

    # 6. Tell Docker that this container wants to listen on Port 3000
    EXPOSE 3000

    # 7. The command that actually runs when the container starts
    CMD ["node", "server.js"]
    ```
  </div>
  <div label="docker-compose.yml">
    ```yaml
    # Docker Compose allows you to boot up your App AND its Database 
    # simultaneously with a single command!
    version: '3.8'

    services:
      my-node-app:
        build: .                   # Build the Dockerfile in this directory
        ports:
          - "3000:3000"            # Map localhost:3000 to Container's Port 3000
        environment:
          - DB_URL=mongodb://mongo-db:27017/myapp
        depends_on:
          - mongo-db               # Wait for the DB to boot first!

      mongo-db:
        image: mongo:latest        # Download official MongoDB image from Docker Hub
        ports:
          - "27017:27017"
        volumes:
          - mongo-data:/data/db    # Save database data permanently on the host hard drive

    volumes:
      mongo-data:
    ```
  </div>
</CodeTabs>

**How to test this:**
Instead of installing MongoDB manually, and running `npm start` manually... you just run:
`docker-compose up -d`

Docker will download MongoDB, build your Node app, link them together on a private internal network, and boot them both in the background. It is magic.

## 10. Common Mistakes

<WarningCard title="Leaking Secrets in Images">
  **The Mistake:** Writing `ENV STRIPE_SECRET_KEY=sk_live_123` directly inside your `Dockerfile`, or copying a `.env` file into the Image.

  **Why it happens:** Developers treat the Dockerfile like a local script and want to make sure the app has access to the database passwords.

  **The Fix:** Docker Images are readable by anyone who downloads them! If you push that Image to Docker Hub, hackers will instantly steal your Stripe key. 
  Images must be completely agnostic. You inject environment variables at *Runtime*, not Build time. Pass them dynamically using `docker run -e STRIPE_SECRET_KEY=...` or via `docker-compose.yml`!
</WarningCard>

## 11. Best Practices

**Docker Volumes (Persistent Data):**
Containers are **Ephemeral** (temporary). If you delete a MongoDB container, every single user in your database is deleted forever! To fix this, you must use **Volumes**. A Volume punches a hole through the Container and saves the database files directly onto your host computer's hard drive. When the container is destroyed, the Volume survives!

**Multi-Stage Builds:**
If you write a React or Typescript app, you need `devDependencies` (like Webpack or the TS Compiler) to build the code, but you don't need them to *run* the code in production. A Multi-Stage Dockerfile compiles the TS code in Stage 1, and then copies *only* the compiled Javascript to Stage 2, throwing away all the heavy compilers. This reduces your Image size from 1.5GB to 50MB!

## 12. Performance & Security

**Security (Root User):**
By default, the `CMD ["node", "server.js"]` inside a Docker container runs as the `root` Linux user. If a hacker exploits a vulnerability in your Node app, they gain root access to the container. 
You should always add `USER node` right before the `CMD` in your Dockerfile. This forces the app to run as a restricted, unprivileged user, vastly shrinking the blast radius of a hack.

## 14. Practice Challenge

**Mini Assignment:**
1. Create an empty folder. Add a file named `app.js` with exactly one line: `console.log("Hello from inside the Container!");`.
2. Create a `Dockerfile`:
```dockerfile
FROM node:18-alpine
COPY app.js .
CMD ["node", "app.js"]
```
3. Open terminal and build the image: `docker build -t my-first-app .`
4. Run the image: `docker run my-first-app`
5. You should see the console log print! You just containerized an application!

## 15. Summary

*   **Docker** packages code and its OS into a portable box.
*   **Dockerfile:** The blueprint script.
*   **Image:** The read-only template built from the Dockerfile.
*   **Container:** The running instance of the Image.
*   **Layer Caching:** Optimizing the Dockerfile to build instantly.
*   **Docker Compose:** A tool to boot up multiple connected containers (App + DB) locally.
