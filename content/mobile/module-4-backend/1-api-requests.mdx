# REST APIs & Fetch

Mobile apps are useless without data. Unless you're building a calculator, your app needs to talk to a Backend API to fetch user profiles, send messages, or process payments.

## 1. Introduction

A backend API (Application Programming Interface) is essentially a web server that returns raw data (usually JSON) instead of HTML. Mobile apps act as the "Client", making HTTP requests (GET, POST, PUT, DELETE) to this server over the internet.

## 2. Why this concept exists

Mobile phones don't have the storage capacity or processing power to hold the entire database of a company like Netflix. Therefore, the phone must constantly ask the server, "What are the latest movies?" and the server responds with a small JSON payload.

## 4. Internal Working: HTTPS

Because mobile apps are used on public Wi-Fi networks (like coffee shops), all API requests *must* use HTTPS (encrypted). If you try to make an HTTP (unencrypted) request in modern Android or iOS, the operating system will block the request at the network layer.

## 7. Real-world Examples

- **Twitter:** When you pull down to refresh, the app fires a `GET /tweets?latest=true` request. The UI shows a spinning loader until the JSON arrives, then the Reducer updates the global state, and the UI re-renders with the new tweets.

## 8. Best Practices

- **Timeout Handling:** Mobile users lose signal often. Set a timeout (e.g. 10 seconds) so the app doesn't hang forever waiting for a response.
- **Show Loading States:** Always show a spinner (ActivityIndicator) while the network request is pending.

## 9. Common Mistakes

- **Not catching errors:** If a user is on an airplane and opens your app, the `fetch` will throw an error immediately. If you don't use a `try/catch` block, your app will hard crash.
- **Leaking API Keys:** Never hardcode secret API keys (like Stripe secret keys) into your mobile app code. Mobile apps can be decompiled. The mobile app should only talk to *your* backend, and your backend should talk to Stripe.

## 12. Summary

Networking is a fragile part of mobile engineering because you cannot control the user's internet connection. Building resilient apps means elegantly handling timeouts, displaying loading spinners, and recovering gracefully when the network fails.
